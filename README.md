# ERP Система для Зоопарка

## Описание проекта
Это учебная ERP система для автоматизации задач зоопарка. Программа помогает управлять:
- Животными разных видов (львы, попугаи, змеи)
- Сотрудниками с разными обязанностями (кормильцы, ветеринары, уборщики)
- Вольерами для содержания животных
- Процессами ухода - кормление, медицинские осмотры, уборка
- Выставками для посетителей
- Отчетностью по всем операциям.
Проект демонстрирует применение принципов SOLID на практике в реалистичном контексте.

## Принципы SOLID в проекте
### 1. Single Responsibility Principle (Принцип единственной ответственности)
Каждый класс должен делать что-то одно.
Как реализовано:
- `Lion`, `Parrot`, `Snake` - только поведение конкретного животного
- `Feeder` - только кормление животных
- `Veterinarian` - только медосмотры животных
- `Cleaner` - только уборка за животными
- `ZooSystem` - только управление системой и отчетность
Если нужно изменить процесс кормления, меняем только класс `Feeder`, не трогая других.

### 2. Open/Closed Principle (Принцип открытости/закрытости)
Классы должны быть открыты для расширения, но закрыты для изменений.
Как реализовано:
- Чтобы добавить новое животное (например, тигра), создаем `class Tiger extends Animal`
- Чтобы добавить нового сотрудника (например, дрессировщика), создаем новый класс
- Существующий код не нужно менять при добавлении новой функциональности.

### 3. Liskov Substitution Principle (Принцип подстановки Лисков)
Объекты дочерних классов должны заменять объекты родительских классов.
Как реализовано:
- Все животные (`Lion`, `Parrot`, `Snake`) могут использоваться как `Animal`
- В массиве `Animal[]` можно хранить любых животных
- Методы, работающие с `Animal`, принимают любых животных.

### 4. Interface Segregation Principle (Принцип разделения интерфейсов)
Лучше много маленьких интерфейсов, чем один большой.
Как реализовано:
- `Feedable` - только для кормления
- `MedicalCheckup` - только для лечения
- `Cleanable` - только для уборки
- Животные реализуют только нужные интерфейсы
Змея (`Snake`) не реализует `Cleanable` т.к. ей не нужна уборка

### 5. Dependency Inversion Principle (Принцип инверсии зависимостей)
Зависеть нужно от абстракций, а не от конкретных классов.
Как реализовано:
- `Feeder` зависит от `Feedable` (интерфейс), а не от конкретных животных
- `Cleaner` зависит от `Cleanable` (интерфейс), а не от конкретных животных
- `ZooSystem` зависит от `Employee` (абстракция), а не от конкретных сотрудников

## Ситуации, при которых появятся проблемы добавления нового функционала
- Животные и вольеры хранятся отдельно, нет прямой связи
- Время кормления и уборки зашито в коде
- Нужно вручную добавлять животных каждому сотруднику
- Отчеты показывают только базовую статистику
- Не учитывается количество корма, лекарств, расходных материалов

## Почему введенные абстракции улучшили качество дизайна
- Простота добавления новых животных, сотрудников
- Можно легко менять сотрудников (один кормилец вместо другого)
- Можно добавлять новые типы ухода без переписывания системы
- Понятные названия интерфейсов
- Логичное разделение ответственности
- Нельзя отправить змею на уборку (если нет интерфейса `Cleanable`)
- Нельзя назначить уборщика для животного, которое не требует уборки
- Один метод `performDailyRoutine()` работает со всеми сотрудниками
- Один список `List<Animal>` хранит разных животных
- Один интерфейс `Feedable` реализуется разными способами
